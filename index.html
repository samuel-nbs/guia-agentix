1. O que é o AgentiX 2.0

Documentação oficial Workshop (13/07) Merge dos dois
Documentação oficial

Definição em 1 frase (decore esta):

"O AgentiX 2.0 é a plataforma interna da BIA Tech para criar, organizar e executar agentes de IA de forma padronizada, auditável e escalável — em vez de prompts e scripts soltos, você monta componentes reutilizáveis e executa tudo em um fluxo controlado."

Merge — posicionamento

Onde o AgentiX se encaixa no ecossistema:

  • AgentiX = plataforma de agentes tech-for-tech (para times de tecnologia).
  • Bridge = a frente de IA para business; também é quem fornece os LLMs que o AgentiX consome.
  • O AgentiX não consome tokens do usuário — o custo é centralizado na plataforma.
Documentação oficial

A evolução: 1.0 → 2.0

  • Antes (1.0): fluxo legado baseado em AutoGen, difícil de entender e manter, definição via YAML.
  • Agora (2.0): runtime consolidado com Agno, modelo OAF-first, definição de componentes em AGENTS.md e execução orientada por sessão.
  • Foco: mais padronização, previsibilidade e manutenção.
  • O suporte a YAML legado existe apenas para migração, não como caminho principal de autoria.
Ganho prático do AGENTS.md: por ser padrão de mercado, o conhecimento que o time já tem de outros harnesses se aproveita direto — sem formato proprietário pra aprender.
Documentação oficial

O que a plataforma junta em um só lugar

  • Criação de componentes de IA (Agent, Team e Workflow).
  • Publicação e versionamento de bundles.
  • Execução com rastreabilidade por sessão.
  • Recursos operacionais: streaming, HITL, artefatos e observabilidade.
Documentação oficial

Analogia da cozinha profissional (ótima para a plateia)

  • O Agent é o cozinheiro especialista.
  • O Team é a brigada de cozinha.
  • O Workflow é a ordem das etapas da receita.
  • A Sessão é uma execução real dessa receita.
Documentação oficial

Base conceitual: LLM puro × Agente

Um LLM sozinho gera texto, resume, explica e traduz — mas não lê arquivos locais, não chama APIs internas, não persiste artefatos nem busca dados em tempo real. Um agente de IA é um LLM configurado com instruções, capacidades (skills) e limites operacionais.

Sem ferramentas (LLM puro) Com ferramentas (Agente) ┌──────────────────────┐ ┌──────────────────────────┐ │ Pessoa em uma sala │ │ Pessoa com acesso a │ │ isolada │ │ computador e recursos │ │ Só pensa... │ │ Pensa e age │ │ Não executa │ │ Executa com contexto │ └──────────────────────┘ └──────────────────────────┘

Resumo prático: LLM puro pensa e responde. Agente pensa, responde e executa ações.

Documentação oficial

Anatomia de um Agent

  • model: define o modelo de linguagem — o "cérebro de raciocínio".
  • instructions: como o agente deve agir — o comportamento esperado.
  • skills: capacidades operacionais — as ações permitidas (ex.: file-io, http-client, web-search).
  • harnessConfig: comportamento de execução (streaming, HITL, memória, guardrails).
  • Variables: valores dinâmicos no formato nome_variavel.
Documentação oficial

Os 3 arquivos-chave do runtime

  • AGENTS.md — o documento onde você escreve "quem são" os agentes e "como eles trabalham". É o caminho principal de definição.
  • manifest.yaml — diz à plataforma "como carregar e executar" esse pacote (bundle). Funciona como etiqueta de compatibilidade interna — não é tecnologia externa.
  • EngineRouter → AgnoEngine — o EngineRouter instancia o AgnoEngine para executar Agents, Teams e Workflows.

Workshop

Skills × Tools (dúvida comum, esclarecida no workshop)

  • A tool não é um objeto separado — ela faz parte da skill. A skill faz o mapping e instrui o agente a usar um determinado script/código.
  • Pense assim: skill = script + instrução de como usar.
  • Hoje tools são escritas em Python; suporte a Java, Node e outras linguagens está planejado.
  • Com o suporte a secrets, dá para criar skills que chamam APIs com credenciais de forma segura.
  • Exemplo real: a skill do GitHub instrui o agente a usar o GitHub CLI — ler PRs, issues, commits, estado de repositório — via API, sem interface.
Workshop

Formas de uso: UI da plataforma + Plugin VS Code

  • Você pode criar e executar agentes pela UI da plataforma (no-code) ou pelo plugin do VS Code.
  • Visão do plugin: fazer o máximo possível sem trocar de janela — construir, enviar e consumir agentes de dentro do VS Code. Na plataforma fica o papel do tenant admin (ex.: aprovação de agentes enviados via plugin).
  • Agente enviado via plugin passa por aprovação na plataforma.
  • Ambientes: laboratório → desenvolvimento → homologação → produção.
Workshop

Modelos (LLMs) disponíveis

  • Os modelos vêm via Bridge: linha OpenAI (ex.: GPT-5/4) e Anthropic (ex.: Sonnet 4.6, Opus).
  • Atualizar/adicionar modelo é simples: requisição à Bridge → deploy em 1–2 dias → configura na plataforma.
  • Não é possível acessar os modelos do AgentiX diretamente pelo Copilot Chat — são frentes separadas (justamente para não consumir tokens do usuário).
Merge

Multi-agentes hoje (importante para não errar na frente da plateia)

  • Suportado: múltiplos agentes orquestrados — a saída de um agente vira input do próximo, controlado pelo Workflow.
  • Não suportado (ainda): sub-agentes (um agente rodando outro agente dentro do próprio contexto). O time avalia implementar se surgirem casos de uso.
  • RAG: existe uma versão built-in básica (similar à V1, com upload de arquivos + embedding). Está em desenvolvimento a integração com a nova plataforma de RAG da BIA Tech (vídeo, áudio, páginas do Confluence, ownership e feedback) — o AgentiX vai plugar nela via API.

Passo 1 — Habilitação AgentiX

Objetivo: vincular centro de custo, projeto Jira e responsáveis para liberar os próximos fluxos.

Preenchimento do formulário, na sequência:

  1. Centro de custo.
  2. Projeto Jira.
  3. E-mail do Gerente — pode ser o gerente departamental ou o gerente direto; o importante é ter o cargo "MANAGER". Valide o e-mail clicando na lupa do campo.
  4. Gestores de acesso do projeto (adicionados pela matrícula).
  5. Justificativa da habilitação.
  6. Revisar e enviar.

Resultado: mensagem de sucesso, acompanhamento pela aba "Consultar", e após a aprovação do gerente o projeto fica apto para solicitar Repositórios e Pipelines. O Gestor de Acesso passa a receber o fluxo de aprovação de acessos.

Documentação oficial

Regra importante: o Gestor de Acesso

  • É o cargo máximo dentro do projeto — está acima do tenant admin.
  • É quem aprova ou reprova solicitações de acesso do projeto.
  • Pode ser a mesma pessoa que o tenant admin, mas não é regra.
  • Pode existir mesmo sem atuar como usuário operacional do AgentiX.
  • Recomendação oficial: atribuir esse papel a Product Owners ou Tech Leads. (Você, como PM, é candidata natural — bom gancho pessoal na apresentação.)
Documentação oficial

Passo 2 — Repositórios e Pipelines

Objetivo: provisionar o repositório no GitHub corporativo e registrar os dados obrigatórios de governança.

  1. Selecionar o projeto Jira habilitado (o mesmo da habilitação).
  2. Preencher todos os campos de governança.
  3. Informar o nome do repositório (seguindo as regras de nomenclatura da plataforma).
  4. Revisar e Finalizar.

Depois do envio: a plataforma dispara e-mail para o time de governança, o repositório é criado no GitHub com o nome informado e a solicitação fica rastreável na aba "Consultar".

Boas práticas da doc: validar a nomenclatura antes de enviar, revisar os campos de governança para evitar retrabalho e confirmar se o Jira selecionado é o mesmo da habilitação.
Documentação oficial

Passo 3 — Acessos AgentiX (perfis)

Objetivo: conceder o perfil adequado para cada usuário do projeto, com aprovação do Gestor de Acesso. A solicitação afeta plataforma e GitHub conforme o perfil.

PerfilEscopo de acesso
VisualizadorSomente visualiza logs e agentes — não executa nem edita nada
ExecutorExecuta o agente, sem poder fazer ajustes ou publicar mudanças
DesenvolvedorConstrói e ajusta os agentes + permissões de desenvolvimento no GitHub

Fluxo de aprovação: solicitação → notificação ao Gestor de Acesso → análise → aprova/reprova → solicitante acompanha o status. Regra operacional: o aprovador é o Gestor de Acesso definido na habilitação, não necessariamente o tenant admin ou o gerente departamental.

O que resolve no dia a dia

Sem uma plataforma, cada time cria prompts e scripts isolados, difíceis de manter. Com o AgentiX você tem:

  • Padrão para descrever agentes;
  • Controle de execução e histórico;
  • Reaproveitamento de componentes em diferentes casos de uso.

Para o desenvolvedor

  • Padrão de mercado (AGENTS.md) — reconhecível em qualquer harness.
  • Plugin VS Code: constrói sem sair do editor.
  • Skills prontas (file-io, http-client, web-search, GitHub...).
  • Secrets para chamadas de API seguras.
  • Versionamento de bundles + rastreio via GitHub.

Para a organização

  • Governança: tenants, aprovação, permissionamento.
  • Observabilidade nativa: logs, status e custos por tenant/centro de custo, modelos usados, nº de execuções.
  • Auditabilidade: histórico completo por sessão.
  • Segurança: guardrails, HITL, MCPs sob controle do banco.
  • Escala: de 1 Agent a Workflows corporativos.

Capacidades operacionais (da doc — decore os 5)

  • Execução por sessão com histórico do que aconteceu.
  • Streaming de eventos em tempo real para acompanhar o andamento.
  • HITL ("Human-in-the-Loop"): validação humana em pontos da sessão antes dos agentes prosseguirem sozinhos até o fim do fluxo.
  • Skills para ações práticas, como ler arquivos e chamar APIs.
  • Observabilidade para acompanhar logs, status e custos.

02:00 – 06:00 • O problema

Por que agentes? Por que uma plataforma?

Antes de mostrar a ferramenta, eu quero alinhar o porquê dela existir. Pensa comigo: um modelo de linguagem sozinho, um LLM puro, é tipo uma pessoa genial trancada numa sala isolada. Ele pensa muito bem, responde, resume, traduz... mas ele não executa nada. Ele não lê um arquivo do seu projeto, não chama uma API interna, não salva resultado em lugar nenhum. Agora, quando a gente pega esse mesmo modelo e dá pra ele instruções, capacidades e limites, ele deixa de só pensar e passa a agir. Isso é um agente de IA: pensa, responde e executa ações. Aí vem o segundo problema, que talvez vocês já tenham vivido na pele: quando cada time começa a criar os seus próprios agentes, cada um faz do seu jeito. Vira um monte de prompt solto, script isolado, sem padrão, sem histórico, sem governança nenhuma. Funciona no notebook de uma pessoa e mais ninguém consegue manter. É exatamente essa dor que o AgentiX resolve, com três palavras que eu quero que vocês levem daqui: padrão pra descrever agentes, controle de execução com histórico, e reaproveitamento de componentes entre os times.🎬 Passa para o slide 3 · pausinha, respira
O contraste "pessoa na sala isolada × pessoa com computador" é da documentação oficial — funciona muito bem num slide com as duas caixinhas lado a lado.
06:00 – 10:00 • O que é o AgentiX 2.0

Definição, história 1.0 → 2.0 e posicionamento

Então o que é o AgentiX 2.0? É a plataforma da BIA Tech pra criar, organizar e executar agentes de IA de forma organizada, auditável e escalável. E vale contar rapidinho a história, porque esse "2.0" tem um contexto importante. O AgentiX 1.0 era baseado num framework chamado AutoGen, e os agentes eram definidos em arquivos YAML — quem usou sabe que era difícil de entender e de manter. Na versão 2.0 a gente consolidou o runtime com o Agno e mudou a forma de definir os agentes: agora tudo nasce num arquivo chamado AGENTS.md. E por que isso importa? Porque AGENTS.md é um padrão de mercado — é o mesmo formato que vocês encontram em praticamente qualquer harness de agentes hoje. Ou seja, o conhecimento que vocês já têm de outras ferramentas se aproveita direto aqui, sem curva de aprendizado de um formato proprietário. Além do AGENTS.md, o bundle tem um manifest.yaml, que é só a etiqueta interna que diz pra plataforma como carregar e executar aquele pacote. E toda execução é orientada por sessão, com rastreabilidade completa — daqui a pouco eu explico o que isso significa na prática. Um último ponto de posicionamento, porque essa pergunta sempre aparece: o AgentiX é a frente tech-for-tech, ou seja, agentes construídos por e para times de tecnologia. Pra casos de negócio existe a Bridge — que, aliás, é também quem fornece os modelos de linguagem que a gente consome.🎬 Passa para o slide 4 (intermediário de transição) · pausinha, respira
10:00 – 16:00 • Como funciona

Agent, Team, Workflow, Sessão + skills/tools, HITL, modelos

🎬 Já passa para o slide 5 — o 4 é só a transição · respira e começaAgora, como isso funciona por dentro. A plataforma tem três blocos de construção, e a lógica é sempre ir do simples pro complexo. O primeiro é o Agent, o bloco mais básico. Todo agente tem três coisas: um modelo, que é o cérebro de raciocínio; instruções, que dizem como ele deve se comportar; e skills, que são as ações que ele tem permissão de executar — ler e escrever arquivos, chamar APIs, buscar na web. E aqui deixa eu esclarecer uma dúvida que apareceu no workshop: "e as tools, onde entram?". A tool não é um objeto separado — ela vive dentro da skill. Pensa na skill como o script mais a instrução de como usar aquele script. Hoje elas são escritas em Python, e já está no radar o suporte a outras linguagens, como Java e Node. E com o recurso de secrets, dá pra guardar credenciais e fazer chamadas de API de forma segura.🎬 Passa para o slide 6 · pausinha, respiraO segundo bloco é o Team: um grupo de agentes colaborando — um analisa, outro escreve, outro revisa. E o terceiro é o Workflow: o fluxo completo, com etapas em ordem, começo, meio e fim. Uma analogia que ajuda a fixar: o Agent é o cozinheiro especialista, o Team é a brigada de cozinha, o Workflow é a receita — e cada execução real disso é uma Sessão. A sessão guarda todo o histórico do que aconteceu, e os arquivos usados ou gerados ficam salvos como artefatos. Outro detalhe que foi pergunta no workshop e vale deixar claro: hoje a plataforma trabalha com múltiplos agentes orquestrados — a saída de um agente vira entrada do próximo, e quem controla essa dança é o Workflow.🎬 Passa para o slide 7 · pausinha, respiraO conceito de sub-agente, que é um agente rodando outro dentro do próprio contexto, ainda não é suportado — se aparecer caso de uso, o time avalia. Duas capacidades operacionais que fazem diferença no dia a dia: o streaming, que deixa você acompanhar a execução em tempo real, e o HITL — human in the loop — que permite configurar pontos da sessão onde um humano precisa validar antes dos agentes continuarem sozinhos. E sobre os modelos: a gente tem as linhas da OpenAI e da Anthropic, fornecidas pela Bridge, e adicionar ou atualizar um modelo é rápido — questão de um ou dois dias. Por fim, dá pra trabalhar de dois jeitos: pela interface da plataforma, que é no-code, ou pelo plugin do VS Code — e a visão do plugin é justamente você construir e enviar seus agentes sem sair do editor; na plataforma fica o papel de aprovação, que é do tenant admin. E um princípio da nossa documentação que eu recomendo de coração: comece sempre com um único Agent. Evolua pra Team e Workflow só quando a complexidade real do caso pedir.
Este é o bloco mais denso — respire entre os sub-temas. A ordem interna é: Agent → skills/tools → Team → Workflow → Sessão/artefatos → multi-agentes → streaming/HITL → modelos → formas de uso.
16:00 – 20:00 • Benefícios e valor

Valor para o dev, valor para a organização + tokens e RAG

🎬 Passa para o slide 8 · respira e começaBeleza, e o que isso tudo entrega de valor? Deixa eu separar em duas visões. Pra quem desenvolve: você trabalha num padrão de mercado que já conhece, tem o plugin do VS Code, skills prontas, secrets pra APIs, versionamento de bundle. E um detalhe que sempre gera pergunta — inclusive foi pergunta no workshop — o AgentiX não consome tokens de vocês. As instruções do agente, uma vez enviadas, ficam na plataforma; você não fica reenviando contexto. E o custo é centralizado na plataforma — hoje o uso está liberado, sem limite. Agora, pra organização: governança de verdade — tenant, aprovação, permissionamento — e observabilidade nativa. O admin do 2.0 já vem dentro da plataforma: o tenant admin enxerga quais agentes rodaram, quais modelos foram usados, quantidade de tokens, número de execuções, tudo segregado por centro de custo. Hoje isso é informativo, não tem rateio — mas dá transparência total. E rastreabilidade: toda execução é uma sessão com histórico completo. Se alguém perguntar "o que esse agente fez e por quê?", a resposta está registrada lá. Ah, e sobre base de conhecimento, que é outra dúvida frequente: a plataforma já tem um RAG nativo — você sobe os arquivos, habilita a indexação, e o agente consome aquilo como base de conhecimento. E em paralelo o BIA Tech está construindo uma plataforma de RAG bem mais robusta — páginas do Confluence, vídeo, áudio — e o AgentiX vai se plugar nela via API.
"Não consome seus tokens" é o argumento que mais gera reação positiva — dê uma pausa depois de falar.
20:00 – 24:00 • Como começar

Habilitação, repositórios e acessos (onboarding)

🎬 Passa para o slide 9 · respira e começaE como é que vocês começam a usar? O caminho é todo pelo BEX. Vocês entram no portal, vão em Marketplace, pesquisam por AgentiX e clicam em acessar. Lá dentro, o onboarding tem três passos, nessa ordem. Primeiro, a Habilitação do projeto: é onde você vincula o centro de custo, o projeto Jira e os responsáveis. Nesse formulário você informa o e-mail do seu gerente — precisa ser alguém com cargo de manager — e define os gestores de acesso do projeto. E aqui tem um conceito que vale a pena guardar: o Gestor de Acesso é o cargo máximo dentro do projeto, acima até do tenant admin. É ele quem aprova ou reprova as solicitações de acesso do time. A recomendação é que esse papel fique com POs ou Tech Leads.🎬 Passa para o slide 10 · pausinha, respiraDepois que o gerente aprova a habilitação, vem o segundo passo: Repositórios e Pipelines — a plataforma provisiona o repositório no GitHub corporativo, já com os dados de governança do projeto registrados. E o terceiro passo são os Acessos: cada pessoa do time solicita o seu perfil. São quatro: Visualizador, que só enxerga logs e agentes; Executor, que executa mas não edita; Desenvolvedor, que constrói e ajusta os agentes e ganha permissão de dev no GitHub; e Admin, que faz tudo isso e ainda aprova o que vai pro tenant dele. Quem aprova essas solicitações é o Gestor de Acesso do projeto. E um aviso prático pra quem já usava o 1.0: a credencial é a mesma de rede, mas a permissão não migra automaticamente — precisa solicitar o acesso ao 2.0. A documentação tem o passo a passo completo com prints, e se travar em alguma etapa, é só falar com a gente.
Este bloco transforma interesse em ação — é o "call to action" da sua apresentação. Tenha o link da documentação pronto para compartilhar no chat.
